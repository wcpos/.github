# Review gate installation

Repository administrators: land the central workflow and script on `wcpos/.github`'s `main`, then copy both `stubs/review-gate.yml` and `stubs/review-gate-publish.yml` to `.github/workflows/` on each repository's default branch (needed for issue-comment and publisher events).

- **Event lane (`review-gate.yml`):** grants only `contents: read` and calls the reusable workflow with `publish: false`. It evaluates and prints the verdict, including API failures, but never POSTs a commit status.
- **Sole publisher (`review-gate-publish.yml`):** default-branch-controlled `workflow_run`, with `actions: read` for the handoff, `statuses: write`, `pull-requests: write`, and `contents: read`. Under per-SHA concurrency it re-reads every open PR sharing the run's head SHA and publishes one aggregate verdict, not a matrix of competing statuses. Any failing PR blocks the shared context. Slow event evaluators cannot overwrite it with stale success. Fork and Dependabot runs need no write token; the publisher uses the base repository token, and a publisher status 403 is a hard failure.

Without a valid target artifact, the publisher first resolves by head SHA, then by a merge commit's second parent, then by the run's head repository owner and branch. The owner/branch fallback requires the PR head SHA to match the SHA being evaluated; a moved branch is not substituted. No matching open PR means no status. Publisher runs post pending before review pagination, then the verdict; merged PRs publish nothing. The publisher never executes code from the triggering run. If a PR edit or rename prevents the event workflow from invoking the publisher, no status is produced for a fresh head: the required context stays missing, not successful.

For least privilege, do not add `secrets: inherit`: the reusable gate needs only `GITHUB_TOKEN`, which GitHub provides automatically, and inherits the caller's permissions rather than requesting write access in the event lane. Require the **commit status context `review-gate`**, not a caller-prefixed check-run name. Every wcpos trunk ruleset already requires conversation resolution (owner ruling, 2026-10-17); `review-gate` is additional, not a replacement. Retain that requirement and disable bypasses.

Ruleset requirement shorthand (not a complete GitHub ruleset JSON document):

```yaml
required_status_checks: review-gate
```

Security notes: the reusable workflow executes only `wcpos/.github`’s own code (sparse checkout of `scripts`), never pull-request code. Pin both stubs’ reusable workflow references to a commit SHA of `wcpos/.github` rather than `@main`; the checkout uses `job.workflow_sha`, so each pin covers the script too. Update each repository’s pin when rolling out gate changes. Residual risk: a same-repository PR could add write permissions to its own workflow and forge the status context. That is a visible workflow edit; the ruleset's required conversation resolution still applies.

Codex refuses `@codex review` posted by `github-actions[bot]` (observed 2026-10-17: account-setup errors). A repository member or the local post-push hook posts the request; the gate only warns and never requests a review automatically. Resolving a thread alone does not trigger these workflows: **RESOLVE FIRST, THEN REPLY**, so the reply's `pull_request_review_comment` event sees the resolved thread. Use `gh workflow run review-gate.yml -f pr=<n>` to rerun evaluation for a stale failure. Before adding the status requirement, backfill existing open PRs in each repository: `for n in $(gh pr list --state open --json number -q '.[].number'); do gh workflow run review-gate.yml -f pr=$n; done`.

Comment, review and dispatch re-evaluations reach the publisher through the `review-gate-target` artifact (`{ "pr": <number>, "sha": "<evaluated head>" }`), uploaded even after a failed verdict. The publisher downloads it from the triggering run and treats it as untrusted data: only a positive safe-integer PR number and a 40-hex SHA are accepted. Only the PR number is forwarded; the evaluator re-reads its live head from the API, never trusting the artifact's SHA. Missing or malformed artifacts use the SHA/owner/branch fallback above.

Dismissed reviews are ignored, and approvals require no body reply. All reviewer-started threads require a reply by another author (bot findings require a non-bot reply); author-started threads still must be resolved. Review-body dispositions require a non-bot top-level PR comment after the review's last edit (or submission if unedited). CodeRabbit's newest review must match the head commit OID. Freshness uses the latest of the head commit date, head force-push, and base change; reviews and Codex states must be at or after that boundary. Codex accepts a completed head-bound state, any head-bound review, or a qualifying receipt. A Codex receipt has no OID: both the latest non-bot request and receipt must postdate the freshness boundary, and the receipt must postdate the request; receipt-based passes carry a warning. Without a request a receipt is not accepted.

API failures in the publisher publish failure when the head SHA and status endpoint are available; if the head cannot be resolved, publication is impossible and the job fails. Event-run API failures print a failed verdict without publishing.
